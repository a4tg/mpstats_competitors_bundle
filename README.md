# MPSTATS: устройство проекта и единый процесс

## Локальное приложение

Добавлена первая версия **Ozon SKU Lab**. Запуск: `run_local_app.bat`.
Она принимает произвольный список SKU/артикулов и ABC-книгу, собирает доступные
данные в пакет CSV + JSON для нейросети, сохраняет историю и подключает существующий
сборщик конкурентов для загруженной подготовленной таблицы запросов.
Инструкция и ограничения: [local_app/README.md](local_app/README.md).
Ниже сохранён исходный разбор скриптов; он описывает состояние до добавления приложения.

Разбор локальных файлов выполнен 15.09.2026. Сетевой сбор не запускался; проверены исходный код, Excel и SQLite в режиме чтения. Описанный ниже единый процесс — проект следующих изменений, а не уже реализованная функциональность.

## Что решает проект

Для собственных товаров Ozon собираются поисковые запросы, затем товары, встречающиеся в выдаче по этим запросам. На основе пересечений строится рейтинг потенциальных конкурентов для каждого собственного SKU.

## Что подтверждено по результату

- Вход содержит 12 886 строк; совпадает с числом строк общей книги после исключения 124 строк без запроса. Наборы из 62 SKU совпадают. Это согласование количества, а не полная проверка происхождения каждой ячейки.
- Разметка входа: 5 265 строк «Да — требуется проверка назначения», 7 621 «Нет / не классифицирован».
- Локальный повтор отбора существующей функцией даёт 619 связей SKU ↔ запрос и 262 уникальных запроса, как в сохранённом отчёте. Ни для одного SKU в этом входе не понадобился возврат к нетематическим запросам.
- Итог от 15.09.2026 13:49:40: 56 245 строк выдачи, 3 100 строк рейтинга, 0 записанных ошибок. Строка рейтинга — пара «наш SKU / SKU конкурента», поэтому это не 3 100 уникальных товаров.
- Балл равен сумме по пересекающимся запросам: `частота / sqrt(позиция) × коэффициент свежести`. Позиция берётся последняя ненулевая, с резервным использованием средней. Это эвристика поискового пересечения, а не подтверждение взаимозаменяемости товаров.

## Что мешает единому и надёжному процессу

1. **Отсутствует подготовка входа.** Не воспроизводятся привязка артикула, границы двух сравниваемых периодов, вычисление показателей и тематическая классификация. Их нельзя достоверно восстановить только по названиям колонок.
2. **Настройки разбросаны.** Разные пути, профили Chrome, фиксированные даты, отдельные состояния выполнения. Настройки меняются редактированием Python.
3. **Периоды не согласованы.** Общая книга содержит 17.08–13.09.2026, а проверенный ответ кэша — 16.08–14.09.2026. URL сборщика выдачи не передаёт даты. Нужно отдельно хранить период исходных запросов и фактический период ответа; не считать их автоматически одинаковыми.
4. **Тематический запрос не гарантирует подходящего конкурента.** Для SKU 1053722060 вторая строка рейтинга — простынь для бани, тогда как первая — средство для мытья бани. В коде нет проверки категории, назначения, объёма или комплектации товара.
5. **Собственные товары исключаются только по входному списку.** Остальные SKU того же продавца могут попасть в конкуренты. В 11 из 62 первых мест указан продавец «ПРЯМОЙ КОНТРАКТ - Официальный магазин». Если это ваш магазин, нужен полный реестр собственных SKU либо подтверждённый идентификатор продавца для исключения.
6. **Фильтры могут молча отменяться.** Если после тематического/сопоставимого фильтра ничего нет, код берёт исходные запросы SKU. Для текущего входа не проявилось, но такое поведение нужно явно отражать в отчёте.
7. **Неполный сбор может выглядеть завершённым.** При 401/403 цикл чтения результатов прерывается, уже поставленные задачи не отменяются, а Excel всё равно формируется. Необработанные результаты не обязательно попадут на лист ошибок. Нужны явные статусы всех запросов и статус полноты запуска.
8. **Кэш не является историей запусков.** Ключ — только нормализованный запрос; новый ответ заменяет старый. В ключе нет рынка, параметров или периода. Авторизация выполняется до проверки кэша, даже когда сеть не нужна.
9. **Названия метрик требуют проверки.** «Заказы 30д» и «Выручка 30д» считаются суммой массивов ответа без проверки длины и периода. Отсутствующие массивы превращаются в нули, что смешивает отсутствие данных с отсутствием продаж.
10. **Запуск не отражает сбои корректно.** BAT возвращает код 0 после завершения Python без проверки его ошибки. Экспортёр перехватывает исключения без ненулевого кода выхода. Это мешает автоматическому управлению этапами.

## Предлагаемый единый процесс

```text
Каталог своих товаров + параметры запуска
  → выгрузка запросов
  → нормализация и проверка данных
  → классификация и отбор запросов
  → сбор выдачи по уникальным запросам
  → исключение своих товаров и проверка релевантности кандидатов
  → рейтинг + отчёт о полноте и качестве
```

### Единые входы

- Каталог: SKU, артикул, название, категория/назначение; при необходимости объём, комплектация и идентификатор продавца. Для надёжного исключения каталог должен включать все свои товары, даже если анализируется только часть.
- Конфигурация: рынок Ozon, период выгрузки, два явно заданных периода сравнения, число запросов и конкурентов, правила фильтрации, пути, срок кэша, число потоков.
- Тематическая разметка: сохраняемые правила или отдельный справочник решений с причиной и версией. До выяснения текущих правил использовать имеющийся подготовленный файл как явно обозначенный импорт.

### Структура после реорганизации

```text
config.json
input/                  каталог и импортированные входы
src/                    экспорт, нормализация, отбор, сбор, рейтинг, отчёт
data/raw/<run_id>/       неизменяемые исходные выгрузки и ответы
data/processed/<run_id>/ нормализованные данные и отобранные запросы
state/                  SQLite и служебный профиль Chrome
output/<run_id>/         итоговый Excel и паспорт запуска
logs/<run_id>/           журнал
run.bat                 единая точка входа
```

Общая книга с 62 листами может остаться удобным экспортом для просмотра; обязательным промежуточным форматом ей быть не нужно.

### Поведение единого запуска

1. Проверить входы, даты, обязательные колонки, дубли SKU и наличие всех товаров.
2. Создать идентификатор запуска и сохранить конфигурацию, хеши входов, версию правил.
3. Выполнять этапы последовательно; продолжать только подтверждённо завершённые задачи того же запуска.
4. Проверять кэш до открытия браузера. Запрашивать авторизацию только при необходимости сетевого сбора.
5. Хранить статус каждого SKU и запроса: ожидает, выполнен, пустой ответ, ошибка, пропущен с причиной.
6. Различать полный и частичный отчёт; показывать ожидаемое и фактическое покрытие. Ошибка запроса не должна превращаться в отсутствие конкурентов.
7. Сохранять отчёт в отдельный каталог запуска, не затирая предыдущий. Дать режим пересборки отчёта из сохранённых данных без сети.

## Порядок реализации

**Шаг 1 — объединить имеющийся рабочий участок.** Общая конфигурация и пути относительно проекта, единая команда, проверка входа, корректные коды выхода, кэш до авторизации, статус полноты, отдельные результаты запусков. Пока вход — существующий подготовленный Excel.

**Шаг 2 — восстановить недостающий переход.** Зафиксировать источник соответствия SKU ↔ артикул, границы двух периодов и критерии тематичности. Реализовать нормализацию выгрузок с проверкой на текущих данных. Нельзя обещать воспроизведение текущей разметки без этих правил.

**Шаг 3 — подключить экспорт к общей команде.** Общие даты, согласованные папки и состояние, проверка полноты экспорта. Объединить использование профиля последовательно, без двух одновременно работающих браузеров с одним профилем.

**Шаг 4 — повысить качество конкурентов.** Исключение полного собственного ассортимента, фильтры назначения/категории, отдельная очередь спорных кандидатов, причины включения в рейтинг.

### Критерий готовности

Пользователь задаёт каталог и период и запускает одну команду. После прерывания тот же запуск продолжается; исходные данные и старые результаты сохраняются. Отчёт показывает покрытие, ошибки, реальные периоды и причины отбора. Повторная сборка из тех же сохранённых входов и версии правил воспроизводит рейтинг.
